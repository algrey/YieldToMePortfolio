# SPK-003 — Future broker-sync threat model

Status: design-spike evidence for `SPK-003` (`TASKS.md`). Requirements: BRK-001.
This document is threat-model evidence, not a durable architecture record —
`docs/ARCHITECTURE.md` §8/§8.1 remains the normative design, and
`docs/DATA_MODEL.md` §8/§8.1 remains the normative (deferred) schema. Nothing
described here is implemented against a live broker: `domain/broker-sync/`
contains pure TypeScript contract types and planning functions only, and no
network call, broker SDK, or credential store exists yet.

## Scope

The future broker/OAuth adapter boundary described in
`docs/ARCHITECTURE.md` §8: authorization/token lifecycle, account listing
and mapping, transaction/cash/position sync, optional entitled quotes, and
disconnection. The broker candidate itself is an explicit assumption — an
AU CHESS-sponsored OAuth-capable archetype, chosen for consistency with the
AUD/ASX-only `docs/Example_Portfolio.csv` because no routed product evidence
names a real broker (see `docs/ARCHITECTURE.md` §8.1). Out of scope: any
specific broker's real API/OAuth surface, which requires its own future
task once a broker is actually selected.

## Assets

- Broker OAuth access/refresh tokens (never modelled as a value in this
  contract — see below).
- Broker-reported transaction, cash, and position data for a user's
  accounts.
- The portfolio ledger's integrity (immutability, correct FIFO/valuation
  inputs).
- The mapping between a broker account and an owned portfolio.
- Any broker-entitled quote data subject to redistribution restrictions.

## Actors

- The authenticated portfolio owner (`user_id` from the verified Cloudflare
  Access identity — see `docs/ARCHITECTURE.md` §4).
- A future broker-sync background job/adapter implementation acting on the
  owner's behalf.
- An attacker attempting cross-user access, credential exfiltration, or
  ledger corruption through a malicious or compromised broker response.

## Deferred to the implementation split (not covered by this spike)

These require a real, approved broker/API before they can be implemented or
tested against actual behavior; they are recorded as proposed follow-up
tasks in `TASKS.md` under "SPK-003 proposed split":

- Real OAuth authorization-code flow, redirect/callback handling, and
  provider-side token refresh/rotation.
- Actual encryption-at-rest implementation for the token envelope (KMS-style
  key, Worker secret, rotation policy).
- Rate-limit/backoff and partial-page failure recovery against a real
  provider's API behavior.
- Provider-specific webhook/push-sync signature verification, if the
  eventually-selected broker offers push delivery instead of (or alongside)
  polling.
- Full quote-entitlement enforcement end-to-end (connection scope actually
  gating `MarketDataProvider` access at the route/repository layer).
- D1 migration for `broker_connections`, `broker_accounts`,
  `broker_sync_runs`, and `external_record_mappings` (`docs/DATA_MODEL.md`
  §8), plus their ownership/ownership-denial repository tests.
