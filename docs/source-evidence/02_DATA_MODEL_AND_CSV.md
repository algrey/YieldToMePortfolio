# 2. Data model and CSV specification

## 2.1 Provenance legend

Every field below is tagged by its likely origin:

- **U** — entered or edited by the user.
- **I** — imported from a file.
- **E** — retrieved from an external market/news data source.
- **C** — calculated by the application.
- **S** — generated by authentication, database or application infrastructure.
- **O** — optional user override of imported/external data.

A field may have more than one origin. For example, a security name can be imported, later refreshed externally, and overridden for display by the user.

## 2.2 Authoritative versus derived data

The authoritative private financial ledger should be:

1. portfolios;
2. portfolio-security associations, including watch-only entries;
3. immutable-or-audited transactions;
4. dividend/interest cash flows and manual overrides;
5. settings.

A **holding is a projection**, not the primary record. Open shares, cost base, average price, realised gain and unrealised gain must be derived from transactions and market data. Storing a mutable `shares_owned` field as the source of truth would allow the ledger and displayed totals to diverge.

Calculated position snapshots may be cached for performance, but must be reproducible.

## 2.3 Privacy boundary

### User-private entities

- users and settings;
- portfolios;
- portfolio-security associations and notes;
- transactions and lot allocations;
- actual dividend/interest receipts;
- forecast overrides;
- alerts;
- import/export jobs and raw row errors;
- cached portfolio/holding history tied to a user's ledger.

### Shareable/global entities

- canonical securities;
- public prices and price history;
- FX rates;
- public fundamentals;
- public announced/forecast dividend events;
- public news articles.

Even when global market data is shared, every query that joins it to holdings must first authorise the user-owned portfolio/security association.

Cloudflare Access establishes who may reach the application. It does **not** by itself enforce record-level isolation inside D1. The Worker must derive the internal user from the verified Access identity and scope every private read/write to that user.

## Row grammar

Each portfolio-symbol group begins with exactly one **definition row**:

- has ID, symbol, portfolio, currency and usually name/exchange;
- has blank quantity, price, date and type;
- creates the portfolio-security association even if no transaction follows.

Zero or more **transaction rows** follow with quantity, price, date/time and Buy/Sell type.

This distinction is essential. Treating every definition row as a zero-quantity transaction would corrupt counts and history; ignoring them would lose watchlists and quote-only instruments.

## Confirmed examples

### Watch-only security

`US watch` contains one definition row for `EPR`, no transaction rows, and a display symbol override `EPR Properties`.

### Cash pseudo-security

`Aus Super` contains `AUD=CASH` with buys and a sell at unit price 1. This should be modelled as cash ledger activity, not sent to a market-price provider.

### FX quote membership

`USDAUD=X` appears as a quote-only definition in more than one portfolio. Symbols can be shared globally while membership remains per portfolio.

### Notes

One transaction row, NCK.AX ID 143, contains `SPP shares`. The importer must preserve notes exactly after normalising line endings.

### Display Symbol

Only EPR uses the field in this file. Blank does not mean “erase provider name”; it means no override.

### Purchase exchange rate

33 transaction rows contain `0`; the rest are blank. A zero conversion rate is mathematically invalid, so in this legacy file it is almost certainly a sentinel for unspecified/automatic. Import zero as `NULL/unknown` with a warning unless a test of the Android app proves otherwise.

### Accounting

Thirteen sell rows specify FIFO. The cash sell has blank accounting. The Add Portfolio form also shows FIFO as the default, and FIFO reproduction exactly matches displayed realised gains.

## Data quality observations

- Names are abbreviated and sometimes poor (`53270` for UTG); retain imported text as an override, but prefer canonical provider metadata where reliable.
- Exchange can be blank for cash.
- Symbols may be unusual or invalid for a current provider (`MAQ.XA`); do not reject solely because a provider cannot resolve them.
- Historical transaction times include `00:00:00`, `18:00:00` and explicit Australian daylight offsets. Do not rewrite the local trade date through an incorrect UTC conversion.
- Commission is zero in every sample transaction, but must still be supported.
- `Accounting Execution Ids` is blank throughout, but should be accepted for round-trip compatibility.
- Blank rows appear between groups and must be ignored without warning noise.

## Cross-source inconsistencies

### RMD.AX

- `01.png`: 3,500 shares, cost A$98,180, average approximately A$28.051.
- CSV: 3,000 shares, cost A$83,680, average approximately A$27.8933.

The screenshot implies an additional 500 shares at A$29 that are absent from the CSV. This is evidence that the sources are different snapshots, not evidence for a formula error.

### Transaction counts

- `07.png` shows Aus Sold 34 and USA 11, matching CSV transaction rows.
- It shows Aus Stocks 63 versus 58 CSV transaction rows, and Aus Super 21 versus 12.

Possible explanations include data captured at different times, additional dividend/interest/cash-flow records not included in this export, or a source-specific counting rule. This requires an Android test.

### Dynamic prices

PLS changes from A$4.265 in `01.png` to A$4.26 in `04.png` and A$4.255 in `06.png`. Corresponding value and daily totals change immediately. This is expected live-data behaviour.

# 2.6 CSV import specification

## Parsing

1. Decode UTF-8 with optional BOM; detect and reject unsupported binary formats.
2. Parse RFC-style CSV with quoted commas/newlines.
3. Trim column-name whitespace and normalise case/spaces for matching.
4. Ignore completely blank records.
5. Preserve original raw values for preview/error reporting.
6. Detect schema by available columns rather than exact count/order.
7. Parse decimal fields exactly; do not coerce through binary float.
8. Parse `Transaction Date` into local date plus explicit offset; keep raw text.
9. Treat blank and legacy zero purchase FX as unknown unless user explicitly confirms zero semantics.
10. Validate type case-insensitively.

## Grouping and entity creation

- Group by normalised portfolio name and source symbol/exchange.
- A blank-quantity definition row creates/updates a portfolio-security association.
- A transaction row may create a missing association with a warning, but the sample always supplies definitions first.
- Duplicate security symbols across portfolios share a canonical `securities` record but get separate `portfolio_securities` records.
- Do not merge two securities solely because their name matches.

## Duplicate strategy

The import preview must require one of:

- **Create new:** create uniquely renamed portfolios where names already exist.
- **Merge:** match portfolio by normalised name and transactions by stable import fingerprint.
- **Replace:** replace selected portfolio ledger only after explicit confirmation and backup/export offer.

Recommended transaction fingerprint when no broker ID exists:

```text
user + portfolio + security identity + type + local date/time + quantity + unit price + commission + currency + source Id
```

The source `Id` helps but should not be assumed globally unique across files.

## Validation rules

Hard errors:

- missing portfolio or symbol on a meaningful row;
- invalid decimal/date;
- unknown transaction type with no mapping;
- sell exceeding owned quantity when shorting is disabled;
- duplicate internal source ID that resolves to conflicting content;
- cross-user object reference.

Warnings requiring review:

- unresolvable provider symbol;
- blank/zero FX for foreign-currency transaction;
- missing exchange/name;
- sale accounting method blank and defaulted;
- transaction time absent;
- unknown optional columns;
- non-chronological source ordering;
- security definition duplicated.

## Atomicity

Use a staging phase:

1. parse and validate into temporary/import-staging records;
2. show preview;
3. commit portfolios, memberships and transactions in deterministic batches;
4. run lot calculation;
5. mark job complete only after post-import reconciliation passes.

If a full database transaction cannot cover the entire import, use an import job ID and visibility flag so partially committed records are not exposed until finalisation; provide cleanup on failure.

## Post-import reconciliation

For every portfolio-security:

- open quantity from transaction ledger;
- remaining cost basis;
- realised proceeds/cost/gain;
- no unmatched sale quantity unless shorting enabled;
- totals equal sum of lots within exact decimal tolerance.

Store warnings and make them accessible after import.

# 2.7 CSV export specification

## New schema requirements

- Include `Schema Version` either as a leading metadata line, a dedicated column, or a companion manifest. A simple dedicated `Schema Version` column is easiest for plain CSV round-trip.
- Use stable, documented column names.
- Export dates in an unambiguous ISO form while preserving timezone, e.g. separate `Transaction Date`, `Transaction Time`, `Timezone Offset` columns.
- Preserve decimal strings without locale commas.
- Quote fields per CSV rules.
- Export definition rows so watch-only securities survive round-trip.
- Export all transaction types supported by the new app.
- Include source/import IDs only as optional provenance, never as database secrets.

## Compatibility mode

Provide a **Legacy MSP format** option if re-import into the Android app is needed. It should reproduce the 17-column supplied schema and optionally the 19-column newer variant.

The default YieldToMe export should be versioned and cleaner rather than perpetuating ambiguous fields.

## Security/privacy

- Export only records owned by the authenticated user.
- Do not place Cloudflare identity, internal user IDs or access tokens in CSV.
- Generate on demand; avoid long-lived public URLs.
- Use a filename such as `yieldtome-portfolios-2026-07-28.csv`.
- Record an audit event without logging portfolio contents.

# 2.8 Data constraints and indexes

Recommended minimum constraints:

```text
users: UNIQUE(access_subject)
portfolios: UNIQUE(user_id, normalised_name) where not deleted
portfolio_securities: UNIQUE(user_id, portfolio_id, security_id) where not archived
securities: UNIQUE(provider, provider_symbol, exchange_code)
transactions: INDEX(user_id, portfolio_id, portfolio_security_id, trade_date, trade_time)
lot_allocations: UNIQUE(sell_transaction_id, buy_transaction_id, allocation sequence)
price_history: UNIQUE(security_id, market_date, source)
fx_rates: UNIQUE(base_currency, quote_currency, as_of/date, source)
```

Every private child row should either carry `user_id` directly or be loaded only through a parent already constrained by `user_id`. Carrying it directly makes safe composite indexes and defensive checks easier.

## Deletion policy

- Prefer soft delete for transactions and portfolios during early development so calculation bugs or accidental user actions can be recovered.
- Exclude soft-deleted rows from all calculations.
- A purge function can be added later.
- Recalculate from the earliest affected trade date whenever a transaction is edited/restored/deleted.

## Audit policy

For financial ledger changes, record:

- actor user;
- object and action;
- timestamp;
- previous/new hash or structured diff;
- import job ID where relevant;
- calculation engine version.

Do not log full private portfolios into generic request logs.
