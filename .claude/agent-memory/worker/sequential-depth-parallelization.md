PRF-003 (2026-08-31, owner-reported slow tab navigation after PRF-001/PRF-002/CALC-005 had already fixed D1 call/statement COUNT): on Cloudflare Workers Free, D1 has no read replication/co-location, so SEQUENTIAL ROUND-TRIP DEPTH is an independent cost axis from call count — a page with few, cheap, already-index-seekable calls can still be slow purely from paying N sequential network hops end-to-end.

**Why:** the owner's report ("3-20 seconds per tab change") persisted even after [[d1-query-planning]]'s call-count fixes landed (root overview flat at 26 statements). Measuring wall-clock waterfall depth (not just call count) was the missing diagnostic.

**How to measure:** a depth-census harness in `tests/prf-002.test.ts` (`depthCensusClient`) wraps the SqlClient so every `all`/`get`/`run`/`batch` call appends a small artificial delay (~8ms) after it resolves before recording its [start,end) interval. This is cheap to add to an existing census test and doubles as the regression guard (assert `depth <= N`).

**Correction (review round 2, same task):** my FIRST version merged transitively-overlapping intervals into one connected "wave" and called the wave count "depth" — reviewer caught that this UNDERCOUNTS: a short call sitting beside a longer sibling, followed by a third call that starts after the short one ends but before the long one does, is a genuine 2-deep sequential chain that the merge conflates into the long sibling's single wave. The correct metric is a longest-non-overlapping-chain DP over the intervals: sort by END time ascending (safe evaluation order — no two intervals can mutually satisfy `end_j <= start_i` and `end_i <= start_j`), then `best[i] = 1 + max(best[j] | end_j <= start_i)`, `depth = max(best[i])`. This is the TRUE critical path — the number of round trips no reordering could avoid given the concurrency actually exhibited. Keep the old merged-component count too if useful, but label it "concurrencyGroups" and never "depth" — it's a real reviewer-caught class of bug, not a style nit, and will look plausible (numbers go down, tests pass) while being wrong.

**How to apply:** when adding or reviewing a loader, check whether a new `await` genuinely consumes a PRIOR read's output. If not, it belongs in the nearest enclosing `Promise.all`, not appended after it. Recurring safe-to-parallelize shapes found in this codebase:
- Independent single-row/count lookups issued back-to-back for no reason other than source-code order (e.g. `portfolio` + `heldCount`, or `settings` + `usdAudRate` + `portfolioList`, all keyed by the same userId/portfolioId but reading different tables).
- A "count-then-fetch" gate pair where the SECOND query's own LIMIT+length-check ALREADY provides the identical fail-closed guarantee the count was checking (found in `historical-portfolio-value.ts`'s FX chain) — the count becomes redundant, not just parallelizable.
- A narrower fallback query whose predicate is a SQL-provable subset of a broader query the caller already ran (found in `owned-holdings.ts`'s `loadCash`) — if the broader one came back empty, the narrower one is guaranteed empty too. Fix by disambiguating "caller never fetched" (`undefined`) from "caller fetched and got nothing" (`[]`) rather than defaulting both to `[]`.
- A whole-portfolio "batched reads, one query per table" section already commented as batchable but implemented as N sequential awaits (found in `owned-dividend-history.ts`) — these are almost always genuinely independent since each populates its own Map merged only after all resolve.
- A DB write followed by a re-read of the SAME row purely to return it, when every field the caller consumes is already knowable from the write's own inputs (found in `db/repositories/identity.ts`'s `touchWithAudit`) — merge in-memory instead of re-querying. Verify no caller depends on a field the write didn't touch, and that removing the read doesn't remove an actual enforcement check (it commonly doesn't, since the write's own WHERE-clause predicate already re-validated the precondition).

**What must stay sequential:** a genuine count-then-fetch gate whose SECOND query is NOT independently bounded (the count exists specifically to avoid ever running the expensive fetch); anything using a PRIOR read's actual VALUE (not just its existence) in its own SQL text or as a branch condition determining whether to run at all.

**PRF-004 addition (2026-09):** the "count-then-fetch where the fetch's own LIMIT+length-check already covers it" pattern above was ALREADY found once, in `historical-portfolio-value.ts`'s FX chain, during PRF-003 — but `docs/ARCHITECTURE.md`'s own PRF-003 write-up then cited `owned-holdings.ts`'s price/FX count queries as the CANONICAL example of a *genuine* dependency, missing that they were the exact same redundant shape. Lesson: finding this pattern once in a codebase does not mean every superficially-similar count-then-fetch pair elsewhere was already checked against it — re-verify each instance against "can the fetch's own bound check answer this?" individually, don't pattern-match on "looks like the same kind of query." Also found a THIRD new safe-to-parallelize shape this round: **firing an independent read as soon as a callee has PARTIALLY resolved enough state, without waiting for the callee's own remaining work to finish.** `domain/auth/request-context.ts`'s portfolio lookup only needs `userId`, which `identity-lifecycle.ts`'s `resolve()` knows well before its OWN `touchWithAudit` write finishes — but the ORIGINAL code structure only exposed `userId` as part of `resolve()`'s final return value, forcing the caller to wait for the whole call (audit write included) before it could even start. Fixed with an optional synchronous callback option (`onIdentityKnown?: (userId) => void`) invoked from INSIDE `resolve()` at the exact point the value becomes known, letting the caller kick off its own concurrent read from inside that callback (which fires and forgets a Promise — JS starts the async operation immediately, no `await` needed inside the callback itself) rather than after `resolve()` returns. This is a more invasive pattern than a plain `Promise.all` reshuffle (it changes a function's public options type) — only worth it when: (a) the value is needed by MORE state than the function's own return already exposes early, (b) the function is called from very few call sites (here: exactly one production caller), and (c) the function's OTHER callers are unaffected by an added optional parameter they don't pass.

**CRITICAL follow-up caveat (PRF-004 review, BLOCKING finding B1) — this "fire early, join later" shape creates an ORPHAN-PROMISE hazard the plain `Promise.all` shape never has.** The eagerly-started promise (`earlyActivePortfolio` above) is only ever `await`ed at a join point placed AFTER the callee (`resolve()`) itself has returned successfully. If the callee instead REJECTS (e.g. `touchWithAudit`'s `client.batch()` failing — a real, if rare, D1-incident class), the join point becomes unreachable, and if the early promise ALSO rejects in that same window, NOTHING ever observes it — Node fires a real `unhandledRejection`, once per affected request, for as long as the correlated failure persists. This is invisible in the happy-path test (the callee succeeds, the join runs, everything looks fine) and only shows up when BOTH the callee and the early read fail together — reviewer needed a dedicated scratch harness with a SqlClient whose `batch()` AND whose target read both reject to catch it. **Fix pattern:** attach a no-op `.catch(() => {})` to the promise as a SIDE OBSERVER the moment it is created — critically, keep the ORIGINAL promise (not the `.catch()`'s own derived promise) as the value stored for the later real `await` join, so that real join still rejects normally with the true error when it IS reached. **How to apply:** any time you fire a promise inside a callback/hook to run concurrently with other in-flight work, and only plan to `await` it later at a point that might not be reached (an early return, a sibling `await` that can itself throw first), add the same-tick `.catch(() => {})` immediately at the fire site — don't assume "I'll `await` it eventually" is enough, since "eventually" is conditional on every earlier step succeeding.
