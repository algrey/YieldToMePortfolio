**Measuring true D1 `rows_read` for a `SELECT DISTINCT`/aggregate query**: `.all()`'s returned-row count massively UNDERcounts D1's real `rows_read` whenever the query dedups/aggregates (e.g. `SELECT DISTINCT market_date`) — D1 bills index entries *visited*, not rows returned. To measure the true cost, capture the exact SQL+params a real code path issued (the `stageCensusClient`/`calls_` pattern in `tests/prf-002.test.ts`), then re-run it as a `COUNT(*)` against the identical `WHERE` clause (drop the `DISTINCT`/`ORDER BY ... LIMIT`) via the raw `node:sqlite` `db.prepare(...).get(...)`. This is the established convention (`tests/prf-002.test.ts`'s PRF-005 test, `tests/prf-010.test.ts`).

**Safe "cheap pre-check before an expensive scan" pattern, when no cheap SQL query can answer the question**: sometimes there genuinely is no index/aggregate trick that answers "is anything missing" for less than the full scan (verify via `EXPLAIN QUERY PLAN` — if the seek is already fully bound by the index, e.g. `(security_id=? AND adjustment_state=? AND market_date>? AND market_date<?)`, the row-visit cost equals the matching-row count; there's no narrower index available). In that case a stored marker is justified — but AGENTS.md's silent-skip lesson (BRK-015 x2, BUG-010, BUG-011) demands the marker never go stale. The safe shape: derive the marker's validity check FROM a live snapshot (fingerprint) of the SAME table every invalidation path already mutates (e.g. `COUNT(*)`/`MIN`/`MAX` of the cache table for that scope), rather than an independently-maintained boolean flag some OTHER write path must remember to clear. This way every existing DELETE/invalidation path invalidates the marker "for free" (it changes the fingerprint), with zero new coupling at N call sites — the exact class of bug that kept recurring. A boundary-only fingerprint (`MAX`/`MIN` alone) is NOT safe if any invalidation path can delete a BOUNDED INTERIOR range (not extending to the tracked boundary) — include a `COUNT(*)` too. Always pair with a hard TTL/cadence ceiling as defense-in-depth, and note in the write-up whether an independent read path already re-verifies on every real access regardless (if so, the marker only needs to bound a background job's OWN staleness, not system-wide correctness).

**CORRECTED (review, 2026-09-02) — a fingerprint over only ONE side of a set-difference "is anything missing" question is not enough, even combined with count+min+max+timestamp.** "Missing" here was `candidates(price_observations) − stored(portfolio_value_history)` — a difference over TWO tables — but the first version of this marker only fingerprinted the SUBTRAHEND (the cache table). A brand-new candidate with NO prior row in the cache (e.g. the day's first price for a date never priced before — the routine daily case, not a corner one) leaves the cache-side fingerprint byte-identical, since there is nothing there to invalidate. **Rule: when "missing" is a difference between two tables, the fingerprint must probe BOTH sides** — here, a cheap `MAX(market_date)` over the candidate side (still just an index seek per `IN (...)` value, not a scan) closes the gap the cache-side snapshot structurally cannot see. Also add a monotonic write-timestamp (`MAX(updated_at)`-style column) to the cache-side snapshot in addition to count/min/max: a delete-then-insert-elsewhere collision (interior delete offset by an unrelated insert, landing count/min/max back on prior values while the actual row set differs) is NOT a far-fetched corner case — it reproduces with only real writers at realistic scale, and count+min+max alone cannot detect it, but a fresh write always advances a timestamp column.

**CORRECTED (review, 2026-09-02) — counting rows RETURNED by `.get()` as "1 row" understates an AGGREGATE query's true `rows_read` by orders of magnitude.** A `SELECT COUNT(*)/MIN/MAX FROM t WHERE ...` always returns exactly one row while visiting every matching row to compute it. When building a rows_read census wrapper (the `tests/prf-002.test.ts` `stageCensusClient`/`tests/hist-001.test.ts` `countingSqlClient` convention), a `.get()` call whose SQL contains a `COUNT(*)` aggregate must read the row's OWN count field as the rows_read contribution, not add 1. This mistake independently produced a false "effectively free"/"100% reduction" measurement that directly contradicted the same PR's own doc comment saying the aggregate "is not free — visits every stored row." When a printed number and an adjacent doc comment disagree about the same code, trust neither until you've re-derived the number.

**New DB table vs. new columns on an existing owned table**: adding a brand-new table in this codebase requires: schema.ts + migration + hand-appended `account_purge_lock_*` triggers (drizzle-kit doesn't generate these; every owner-scoped table needs a migration-embedded trigger, see `0054_hist_002_portfolio_value_history.sql`) + an entry in `db/repositories/account-lifecycle.ts`'s `OWNED_TABLES` (export classification) AND `PURGE_TABLES_IN_FK_ORDER` (child-before-parent purge order) + passing `tests/ops-003a.test.ts`'s "schema-derived export classification covers every table" completeness check. Adding nullable COLUMNS to an ALREADY-owned table (e.g. `portfolios`, which already has purge-lock triggers covering the whole row) needs none of that — just schema.ts + migration. For a small piece of bookkeeping state scoped 1:1 with an existing entity, prefer new columns on the existing table; it's dramatically cheaper and lower-risk. See `historyCompleteFrom` on `portfolios` as the established precedent for a nullable per-portfolio marker column.

**PRF-010 specifics** (as of 2026-09-02, migration `0058`, corrected same day after review): `portfolios.value_history_backfill_verified_at`/`...verified_fingerprint`, checked/written by `app/historical-portfolio-value.ts`'s `backfillStoredValueHistoryForPortfolio` via `db/repositories/portfolio-value-history.ts`'s `loadPortfolioConvergenceMarker`/`loadValueHistoryConvergenceFingerprint`/`recordPortfolioConvergenceMarker`/`convergenceFingerprintMatches`, plus `app/historical-portfolio-value.ts`'s `loadCandidateMaxDate` (the candidate-side half). Fingerprint = `rowCount:minValueDate:maxValueDate:maxComputedAt:candidateMaxDate`. Only ever written when a full check finds `missingDates === 0` (never merely "budget exhausted, some dates unresolvable") — this is what keeps BUG-010 follow-up (e)'s permanently-unresolvable-date tell visible instead of getting silently skipped. Measured, honest costs (`tests/prf-010.test.ts`): full check ~52,040 rows_read/tick; skipped tick ~2,620 (dominated by the cache-side aggregate, itself visiting every stored row — never assume an aggregate is free). `CONVERGENCE_RECHECK_INTERVAL_MS` is 6 hours, the PRIMARY backstop for the one remaining accepted gap (an interior candidate addition, e.g. a backdated historical price import, which moves neither fingerprint half) — not defense-in-depth on an otherwise-complete signal.
