- Correlated `EXISTS`/`NOT EXISTS` against a large, ever-growing table defeats an otherwise-seekable composite index — rewrite as `A.key IN (SELECT B.key FROM B WHERE ...)` or a JOIN.
- Fetching/validating a large table's FULL row set purely to answer a narrow yes/no question is real CPU waste even when the query is already index-seekable (SEARCH, not SCAN) — prefer a `DISTINCT`/`COUNT`/narrow-column query over the identical predicate before paying for the full read.
- A `count(*)` precheck before a fetch is only "genuine" (non-redundant) if the fetch's own `LIMIT MAX+1`/`.length` check can't answer the same "too many?" question itself — when it can, drop the precheck (PRF-004's finding, corrected an earlier PRF-003 doc claim).
- Two calls resolving the SAME authenticated identity in one request doubles a REAL WRITE cost (`touchWithAudit`'s UPDATE/UPDATE/INSERT batch), not just a read. Pattern recurs constantly: a page calls `loadAuthenticatedWorkspace(portfolioId)` purely as an auth gate, then calls `getAuthenticatedSqlContext(portfolioId)` a second time to get the `client`/`userId` its own loader needs. Fix: `loadAuthenticatedWorkspace`'s optional third-arg `sqlContextOut: { current: AuthenticatedWorkspaceSqlContext }` output slot recovers the already-resolved client/userId — drop the second call entirely. **This defect recurs on any newly-added page that copies an older page's auth boilerplate without noticing PRF-002 already fixed the canonical five/six pages** — always grep new/uncensused pages for `getAuthenticatedSqlContext(` sitting right after a `loadAuthenticatedWorkspace(` call with no `sqlContextOut` third arg. Found and fixed again in [[prf-005-income-pages]] on 4 holding sub-tab pages PRF-002 never touched.
- D1 enforces SQLite compile-time limits (`SQLITE_LIMIT_LIKE_PATTERN_LENGTH`, `SQLITE_LIMIT_VARIABLE_NUMBER`, ~100 bound params) that local `node:sqlite` test builds do not raise identically — cap every generated placeholder list defensively (100) regardless of local test coverage. Pre-existing violation noted but never fixed: `MAX_SECURITIES = 500` IN-list caps contradict this (harmless only because production has 18 securities).
- **Multi-window BETWEEN pattern** (used in `app/historical-portfolio-value.ts`'s `loadFacts`, PRF-005): when a function needs price/FX data for N SEPARATE small date windows (not one contiguous range) — e.g. one bounded-tolerance lookback per FY-end date — reading `[minDate, maxDate]` as ONE window still scans everything BETWEEN the windows if they're spread years apart. Instead build `windows: {from,to}[]` (one per requested point) and OR them together in one query: `(col BETWEEN ? AND ?) OR (col BETWEEN ? AND ?) OR ...`. SQLite still uses the index (confirmed via `EXPLAIN QUERY PLAN`, no `SCAN` observed) as long as the leading index column(s) stay pinned by an equality predicate (here: `security_id IN (...)` + `adjustment_state = 'raw'` ahead of `market_date` in the composite index). An empty windows array (`[]`, as opposed to `undefined`) is a distinct "fetch nothing" signal — reuse the existing `securityIds.length === 0`-style short-circuit rather than emitting an OR of zero clauses (invalid SQL).
- Before trusting a function's own doc comment that says "this path doesn't need the fix, not implicated in the reported symptom" — re-check it against the CURRENT bug report. PRF-003's own comment on `loadFacts` explicitly deferred narrowing `loadHistoricalPortfolioValueAtDates`'s window with "not implicated in this task's reported symptom" — that stopped being true once the owner hit Error 1102 loading `/income`, which calls exactly that function. Doc comments recording a scope boundary are a snapshot of the PR that wrote them, not a permanent verdict.
- **Fixture FK/NOT-NULL gotchas when seeding new tables into `productionScaleFixture()` (tests/prf-002.test.ts)**: check the drizzle migration SQL's exact column list before writing an INSERT — column order in `CREATE TABLE` is not obvious from `db/schema.ts` alone, and a `NOT NULL` column with no default (e.g. `dividend_events.created_at`) silently isn't apparent from the domain-layer comments; grep the migration file (`grep -n "CREATE TABLE .dividend_events." -A 25 drizzle/*.sql`) and count columns against your INSERT's placeholder list before running. `node:sqlite` throws a normal constraint error on a missing NOT NULL column, not a helpful "missing column" message — easy to misdiagnose.
- **D1 has (at least) two distinct row-cost dimensions that a query-plan-narrowing fix does NOT necessarily reduce together: rows READ (index/table b-tree entries D1 walks internally, metered against the 5M/day Free-plan billing allowance) vs. rows RETURNED (what actually crosses back to the Worker, gets JS-validated/marshalled — the dimension that drives Worker CPU time and error 1102).** Narrowing a predicate from ONE contiguous `BETWEEN` range to MULTIPLE OR'd `BETWEEN` ranges on the SAME column (the multi-window pattern above) reduces rows RETURNED but can leave rows READ essentially unchanged or even make it worse: confirmed via `EXPLAIN QUERY PLAN` in this repo — a single-window seek pins the range column into the index seek itself (`... AND market_date>? AND market_date<?`), but 2+ OR'd windows on that column make SQLite drop it from the seek bound entirely (`... (security_id=? AND adjustment_state=?)` only, no `market_date` term) and apply the OR'd ranges as a post-seek residual filter — so D1 still walks the FULL per-security-id index range internally. Before writing ANY claim like "reduced rows read by Nx", run `EXPLAIN QUERY PLAN` on the actual N-window SQL (not just the N=1 case) and check whether the narrowing column still appears inside the `SEARCH ... USING INDEX (...)` parenthetical — if it drops out for N>=2, the honest claim is "rows returned dropped, rows read did not." This class of dimension-mismatch was reviewer-caught in PRF-005 (commit 4cd3692 → corrected in 3347479) after a first-pass claim conflated the two.
- The depth (sequential round-trip chain) metric and the CPU/row-volume metric are SEPARATE axes — see [[sequential-depth-parallelization]]. A page can have real, unavoidable depth (e.g. `loadHistoricalPortfolioValueAtDates` must run AFTER `loadOwnedDividendHistory` resolves the FY calendar, so it can't be parallelized with holdings/history) while still being fully fixed for a CPU-limit (Error 1102) class defect, because CPU cost tracks ROWS READ, not ROUND TRIPS. Don't over-invest in chasing depth to zero when the reported symptom is a CPU limit, not latency.
