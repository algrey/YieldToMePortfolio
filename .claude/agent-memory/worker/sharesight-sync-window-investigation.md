Sharesight's real query params for both `ListPortfolioTrades` (v2.1.0) and `ListPortfolioPayouts` (v2.0.0) are `start_date`/`end_date`, NOT `from`/`to`. `domain/sharesight/client.ts`'s `toSearchParams` sent the wrong keys pre-BRK-015 — every call silently fell back to the server's full-history default (`start_date` = portfolio inception, `end_date` = today), which was the actual root cause of the owner's "syncs back to 2019 every time" complaint, not a design gap. Confirmed two ways: (1) `markcatley/sharesight.rs`'s Swagger-derived docs (fetch via `raw.githubusercontent.com`/`api.github.com` — both allowed in-sandbox, no `dangerouslyDisableSandbox` needed), and (2) a live GET-only spike against the owner's real account (`api.sharesight.com` is NOT in the sandbox's allowed hosts, so this step needs `dangerouslyDisableSandbox: true`) — a narrow window under the wrong keys still returned the full 119/107 counts; the same window under the corrected keys returned only 2. Before trusting any Sharesight param/behavior claim in a future task, verify it the same way (docs + live) rather than assuming the existing code's param wiring is correct just because types compile.

A Sharesight payout's identity key (`domain/sharesight-sync/transform.ts`'s `payoutIdentityKey`) is `sharesight-payout:<sharesightPortfolioId>:<holdingId>:<paidOnDate>` — the Sharesight payout `id` is NOT part of it (only appended to `notes` for visibility, lost after commit since `dividend_manual_records` has no notes column). A test asserting "did this specific payout commit" must match on portfolioId/holdingId/paidOnDate, never on the payout's own `id` string, or it will pass for the wrong reason or fail looking for text that was never written to `source_reference`.

**Why:** these are easy to get wrong quietly — the wrong query key still returns 200 OK with a plausible-looking (just unfiltered) result, and the id-based assertion also silently "just returns false" rather than erroring, so neither mistake surfaces as an exception.

**How to apply:** for any future Sharesight-integration task, re-verify param names/response shape against live evidence before designing around them, and always check `transform.ts`'s actual fingerprint/identity-key construction before writing a test or query that filters `transactions`/`dividend_manual_records` by content — don't assume the wire `id` survives into `source_reference`.

See [[test-runner-constraints]] for the general node:test / sandbox pattern this investigation also used (temporary throwaway spike script in `scripts/`, deleted after use, never committed).

**Review-round finding (same task, B1 BLOCKING): a single shared `MAX(...)` watermark across two independently-advancing streams (trades vs. payouts) silently lets the FASTER stream govern the SLOWER stream's fetch window** — the exact "silent permanent skip" shape this task's own load-bearing hazard was designed to prevent, just reached cross-stream instead of cross-sync. Whenever a design derives ONE cutoff/watermark from a `UNION`/combined `MAX` over rows that belong to conceptually separate streams advancing at different rates, check whether each stream needs its OWN independently-computed value instead — a single shared subquery is a strong smell here even when it looks like an elegant simplification.

**Second review-round finding: `listPayouts`'s `start_date` filters by EX-DATE (`goes_ex_on`), NOT paid date (`paid_on`)** — confirmed live via a targeted probe (call with `start_date` = a known payout's own paid date; if it filters by paid date the payout stays in the result, if by ex-date it drops out). This mattered because the app's own watermark is derived from `payment_date` (paid date) — an overlap-days constant computed naively from paid-date deltas overstates real coverage once run through an ex-date filter by however many days separate ex-date from paid-date for that payout (observed up to 62 days on the owner's account, every payout examined had a nonzero gap). When an overlap/lookback constant crosses between two different date fields like this, size it explicitly for the WORSE field's filter behavior, document the gap accounting in the constant's own doc comment, and re-derive live rather than assuming a "paid"-shaped filter param name actually filters that field.
