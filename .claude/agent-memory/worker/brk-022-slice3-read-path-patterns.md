Implemented BRK-022 slice 3 (2026-09-05): Sharesight `sharesight_pending_payouts` announcements fed into `deriveDividendHistoryForSecurity` as `DividendManualRecordFact`s with a new `announcedUnpaid: true` flag.

**Second discriminator, not a repurposed one.** `history.ts` splits owner-typed vs imported tier by `importBatchId === null` (DIV-004). A pending-payout fact never went through a CSV batch, so `importBatchId` stays honestly `null` — but it still needed the imported tier (provider evidence, not owner-typed). Fix: OR a second flag into both filter predicates (`record.importBatchId !== null || record.announcedUnpaid === true`) rather than repurposing `importBatchId` itself. Same pattern would apply to any future non-CSV "imported-tier" fact source.

**Hard-coded `status: "ex_date_passed"` sites vs the date-derived one.** `history.ts` has exactly 3 row-construction sites: the main per-event loop (`status = lifecycleStatus(event.exDate, today)`, date-derived, correct already for an event-anchored fact) and two that literally hard-code `"ex_date_passed"` (`pushEventlessRow`, and the excluded-event resurfacing pass) on the theory that any owner/imported fact IS payment evidence. A fact that is NOT payment evidence (an announcement) only needs the two hard-coded sites patched to `fact.announcedUnpaid ? "declared_pending" : "ex_date_passed"` — the date-derived site needs no change, since a real event's own exDate already governs status correctly regardless of which fact won the row.

**[[census-test-plus-one]]** — any new read added inside `app/owned-dividend-history.ts`'s batched `Promise.all` wave bumps `stats.calls`/`stats.statements` by exactly 1 on EVERY page that transitively calls `loadOwnedDividendHistory` (`/income`, `/income/multi-year`, `/income/assumptions`, `/income/dividends`, the per-security Dividends tab) — grep `tests/prf-002.test.ts` for every `EXPECTED`/`assert.equal(stats.statements, N)`/`DEPTH_CEILING` pin touching those page names before declaring done; `DEPTH_CEILING` itself is a `<=` ceiling so a same-wave addition usually doesn't need a depth bump, only the exact-count pins do.

**[[source-shape-regex-pin-loosen-dont-delete]]** — `tests/ui-006c.test.ts` pinned `/>\s*not paid\s*</` directly against a component's SOURCE TEXT to prove "not paid" renders as literal text, not colour alone. Adding a conditional suffix inside the same `<span>` (e.g. `{row.announcedUnpaid ? " · announced (Sharesight)" : ""}`) breaks the `\s*<` tail. Fix by loosening to `/>\s*not paid[\s\S]*?</` (still proves the literal text exists) rather than deleting the pin — the same shape recurs whenever a status span gains a conditional trailing note.

**Hand-typed `DerivedDividendRow`/`FyDividendTotal`/`OwnedDividendListRow`/`CurrentFinancialYearRow` test fixtures break silently at `tsc`, not at runtime.** Adding a required field to one of these types breaks every test file with a local `row()`/`fyTotal()` builder function typed with an explicit return-type annotation (`function row(...): DerivedDividendRow`). Grep `": DerivedDividendRow\b"`, `": FyDividendTotal\b"`, `": OwnedDividendListRow\b"` etc. across `tests/*.ts` — object literals passed as untyped JSON props to a `renderComponent` harness (execFileSync+tsx) do NOT get caught by `tsc --noEmit`, only by a runtime crash if the component code does something like `parseDecimal(undefined)` — see the next entry.

**Always use `?? null`, never `=== null`, when reading a new optional/nullable field inside a component that might receive props from an untyped JSON-prop test harness.** A pre-existing test's hand-typed props object (built before the new field existed) supplies `undefined`, not `null`. `if (field === null) return x;` lets `undefined` fall through to the next branch and crash (e.g. `parseDecimal(undefined)` throws "Invalid decimal string"). This is not just a test-fixture nicety — it is the SAME shape a legitimately-older stored/cached value would produce in production, so `?? null` is the correct guard either way, not just a test workaround.

**Testing `income-multi-year.tsx`'s merge logic needs a REAL `projectMultiYearIncome` output, not hand-JSON.** The component re-runs `projectMultiYearIncomeWhatIf(multiYearBaselineInput, ...)` on every render (including the harness's static-markup mount) to produce `activeProjection`. A hand-typed `multiYearBaselineInput.assumptions` that doesn't match `MultiYearProjectionAssumptions`'s real shape fails that internal recompute silently (`activeProjection.ok: false`), which falls back to the DIV-011 standalone "(to date)" row and silently defeats any test asserting the MERGED row's text. Build `multiYearBaselineInput`/`multiYear` via the real `projectMultiYearIncome(input)` call (mirrors `tests/div-013.test.ts`'s `baseAssumptions`/`baseline` fixture), never inline JSON.

**`computeSecurityDividendForecast`'s `transactions` input drives its OWN zero-shares early return, independent of what was fed to `deriveDividendHistoryForSecurity`.** If a test passes `transactions: []` to the forecast call while using a real holding for the derivation call, `currentSharesDecimal` resolves to `"0"` and the forecast short-circuits to a fully-zeroed result (including `declaredEventCount: 0`) regardless of how many declared rows exist in `historyRows`. Pass the SAME holding-transactions array to both calls.

See [[sharesight-sync-observation-table-pattern]] for the slice-1/2 (schema + sync) side of this same feature.

**Slice 3 review-correction round (2026-09-05), additional patterns:**

**A "same predicate as X" doc claim needs X's actual SQL checked, not assumed from its name.** The slice-3 docs/comments claimed the read-path suppression reused "the same predicate `loadCommittedSharesightRowValues` uses (non-reversed/non-superseded)". Neither half was true: that function's OWN `dividend_manual_records` query (`db/repositories/sharesight-sync-state.ts`) has NO supersession filter at all (unlike its sibling `transactions` query, which does filter `status <> 'reversed'`) — it's a different query, coincidentally answering a similar question. The real reason a reversed record can't interfere is structural, not predicate-matching: `db/repositories/import-reversal.ts` HARD-DELETEs `dividend_manual_records` rows for a reversed batch (no reversed-row concept exists for that table, unlike `transactions`). When a comment claims two functions "share a predicate," grep both queries side by side before trusting the claim in a doc rewrite too.

**Redefining an aggregate's membership test (`row.announcedUnpaid` → `row.status === "declared_pending"`) is a one-line diff with a big blast radius — grep every site the OLD field name governed before generalizing.** F3's ruling changed what counts as "unpaid" from a synthetic flag (only true for Sharesight-announcement-backed rows) to a status derived from the SAME `lifecycleStatus(exDate, today)` every ordinary provider-declared row already computes. Because `status` was already correct for every row (event-anchored rows get it from the real exDate regardless of source), the fix was purely `aggregations.ts`'s filter predicate — no change needed anywhere `status` was already being computed. The trap is assuming you need to touch history.ts's row-construction sites too; you don't, when the target field is already populated correctly and only the CONSUMER was reading the wrong flag.

**A DIV-007-style "absent field ⇒ inferred value" heuristic derived from one evidence class (paid/confirmed records) does not automatically generalize to a sibling fact type (announcements) sharing the same shape.** `deriveAbsentImportedFranking`'s zero-franking inference was validated against the owner's real *confirmed* Sharesight payouts; nothing about that evidence says an unconfirmed announcement's eventual franking will also be zero when omitted. The fix is a one-line early-return keyed off the discriminator field (`original.announcedUnpaid === true`) placed BEFORE the inference branch, preserving the existing unreadable-value short-circuit above it. When reviewing any "absent X inferred as Y" function, check whether ALL its callers' fact types actually match the evidence base the inference was validated against.

**A `renderComponent`/`execFileSync+tsx` UI test harness stringifies props via `JSON.stringify`, so adding a required field to a TS prop type does NOT break existing test fixtures at compile time — only at `tsc` for TYPED fixtures (see the earlier `DerivedDividendRow`/`CurrentFinancialYearRow` entry above), and NEVER for these render-harness object literals.** Adding `pendingSuppressedByProximityCount`/`pendingTruncated` to `OwnedIncomeProjection` required zero edits to any pre-existing `MINIMAL_PROJECTION`-style JSON fixture; the component just read `undefined` for the missing field, and `undefined > 0` / `if (undefined)` both evaluate falsy — no crash, no rendered disclosure, silently correct for old fixtures. Only add the new field explicitly to the shared fixture object when a later test in the same file needs to override it away from that implicit default.

**A "zero-identities early return" and the main derivation loop are TWO independent code paths that must each get their own fix and its own test.** F5's bug was that a portfolio-wide `identities.length === 0` shortcut skipped a whole batch of reads (including the pending-payouts fetch) that the main loop's OWN zero-security-count branches (unresolved/hidden) already handled correctly. When a loader has both an early-return fast path and a main loop, grep for every `return {` in the function and check each one carries every field/side-effect the "real" path does — the two are easy to let drift out of sync one feature at a time.

**Round 2 correction (2026-09-05): a "make field X paid-only" fix must audit EVERY other field on the same row for consistency, not just the one field a review comment named.** B1 round 1 made `income-multi-year.tsx`'s `mapCurrentRow` `grossDecimal` paid-only but left `cashDecimal`/`frankingDecimal`/`yieldPercentDecimal` as the full FY-to-date figures — an internally-inconsistent row (gross $250 next to a yield computed from $300/$10,000 = 3%, which reads as wrong against the $250 gross). The Orchestrator's fix: revert ALL FOUR fields to the full FY-to-date figures (consistent with each other and with `income-landing.tsx`'s FY-so-far row), and express the paid-only number through the row's OWN already-existing, separately-labelled `actualToDateGrossDecimal`/`actualToDateSourceLabel` slot instead — the same slot the merged-forecast path (`mergeCurrentFinancialYear`) already used, so both paths now read identically. General lesson: when a "make this figure paid-only/net/adjusted" fix touches one field of a multi-field row object, check every SIBLING field derived from the same underlying row for an inconsistency the isolated fix would introduce, and prefer routing the adjusted number through an existing dedicated slot over overloading a field that other fields still assume is the full figure.

**This repo's UI tests for `income-multi-year.tsx` (and likely other components with a `useState`-gated `<dialog>`) cannot assert the row-detail dialog's rendered content.** The dialog only exists in the JSX tree when `selectedRow` (component state, default `null`) is non-null, set via an `onClick` handler. Every render test in this repo uses `renderToStaticMarkup` only (no jsdom/interactive-DOM layer — explicitly documented in `tests/div-013.test.ts`'s file header: "this harness has no jsdom/interactive-DOM layer... so 'typing'/'clicking Apply' cannot be simulated"), so a click that would open the dialog cannot be simulated, and no existing test in the codebase opens this or a sibling dialog. When a task asks to assert dialog-only content, the practical options are: (a) assert what the table row itself renders instead (often enough to prove the underlying data is correct, since the dialog reuses the same row object), (b) add a comment documenting the harness limitation and why the table-level assertion stands in for it, or (c) escalate if the task genuinely requires dialog-only verification — do not silently skip the requirement without a documented reason. This is exactly the `tests/ui-006c.test.ts` source-shape-regex-over-`readFile`d-component-text pattern (see the entry above), reused for dialog JSX specifically.

**Polish round (2026-09-05): "populate a derived slot only when it differs from the figure already shown" needs its own boolean gate, not just reuse of the existing subtraction helper.** `mapCurrentRow`'s `actualToDateGrossDecimal` (paid-only) was always populated whenever the fallback "(to date)" row rendered, even when `dividendUnpaidCount` was 0 — in that case `paidOnlyGrossDecimal(row) === row.dividendGrossDecimal` exactly, so the UI printed the identical dollar figure twice ("$300.00 · $300.00 received so far this FY"). Fix: a small `hasUnpaidSubset(row)` predicate (count non-zero AND gross present AND non-zero via `isZero(parseDecimal(...))`, domain's `../../domain/calculations/decimal.ts` export) gates BOTH `actualToDateGrossDecimal` and `actualToDateSourceLabel` to `null` when false — nulling only one of the pair would leave the render condition (`actualToDateSourceLabel !== null`) still true with a `null` gross, printing "null received so far this FY"-shaped garble. General lesson: a "derived redundant-with-the-original figure" bug needs a dedicated presence/distinctness check, not just relying on the existing derivation to naturally suppress itself.
