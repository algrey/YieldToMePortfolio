This codebase already has a load-bearing pattern for "flag a probable duplicate without ever auto-skipping it," and it recurred exactly on BUG-011 (cross-route CSV/Sharesight trade duplicate) after DIV-004 established it for dividends. Recognize it fast next time rather than re-deriving:

1. **New `ImportReconciliationIssue` code, `severity: "warning"` (or `"info"`), never `"error"`.** `preview.ready` is `!issues.some(error)`, so a warning never blocks readiness/commit by construction — this is how "decision surface, never automatic skip" gets enforced structurally, not by remembering to check a flag somewhere.
2. **New optional `existing<X>Entries` field on `ImportReconciliationInput`**, populated by the caller (only `app/import-actions.ts`'s `loadReview`, via a `client.all` query scoped to `user_id`) — the reconciliation function itself never queries the DB.
3. **The check goes in `createImportReconciliationPreview`'s per-row loop**, guarded so it only fires for the row shape it applies to (e.g. `!isDividend && !isCash && (type === "buy" || "sell")`), using the row's own already-resolved `membershipId`/portfolio-security id, never re-deriving identity.
4. **MUST be excluded from `domain/imports/review.ts`'s `hashedPreview` filter** (the `issue.code !== "..."` list) — this is the single easiest thing to forget and it is NOT optional. Reason: `existing<X>Entries` is only ever supplied by the page/refresh preview path; the ready-service, security-verification-service, and import-commit `revalidate()` paths call `buildImportReview` without it. If the new code's presence changed `previewVersion`, those paths compute a different hash than the page rendered, permanently 409ing the batch's ready/commit with no recovery path. Grep `hashedPreview` in `review.ts` and add the new code right next to `DIVIDEND_NEAR_EXISTING_ENTRY`/`TRADE_NEAR_EXISTING_ENTRY`.
5. **Decimal comparisons use the file's own local `decimal()`/`align()` primitives**, never `Number()` or literal string equality — `"100"` vs `"100.00"` must compare equal (AGENTS.md). `reconciliation.ts` already has these helpers private/unexported; add a small wrapper (e.g. `decimalEqual`) rather than duplicating the alignment logic.
6. **No component change needed** — `app/components/import-review.tsx` renders `review.preview.issues` generically (code/message/row-facts), so a new advisory code just appears in the existing list automatically.

See [[import-commit-polymorphic-fk]] for the commit-time (not preview-time) half of this codebase's dedupe machinery, and BUG-011/DIV-004 in `docs/CSV_IMPORT_SPEC.md` for the two concrete instances of this pattern.

**When investigating "does X close a dedupe gap" claims**: don't assume a key-format change fixes cross-route collision just because it looks "more economic." BRK-005C's Sharesight payout key (`sharesight-payout:<portfolioId>:<holdingId>:<paidOnDate>`) fixed a WITHIN-route idempotency bug (unconfirmed→confirmed churn) but did NOT close the CSV-vs-Sharesight cross-route gap, because the CSV dividend key (`import-fingerprint:<sha256>`) is a structurally unrelated format with no shared component. Check the actual key-construction code on both sides before concluding a gap is closed.

**Review-round follow-ups on BUG-011 added more load-bearing details worth checking proactively next time (don't wait for a reviewer to find them):**

7. **`status = 'posted'` alone does NOT exclude a reversal's economic footprint.** `ledger.reverse()` (`db/repositories/ledger.ts` or wherever the reversal path lives) re-runs `prepareLedgerPosting` on the ORIGINAL input to build the compensating mirror row — that mirror is ITSELF `status = 'posted'`, with the identical type/quantity/price/date/`portfolio_security_id` as the reversed trade, distinguished only by `reverses_transaction_id` being set. Any "existing posted X" query written for a dedupe/duplicate-style check needs `AND reverses_transaction_id IS NULL` too, or a genuine reverse-then-re-import (a real, prescribed remediation path) falsely re-triggers the very check meant to help.
8. **An unbounded "load every existing X for this owner" read added to an existing `Promise.all` in a preview/loader path needs a cap — but do NOT scope it to `batch.targetPortfolioId` to shrink it.** (CORRECTED after a full extra review round: an earlier version of this note recommended exactly that scoping, and it was wrong.) `portfolioFor` (`domain/imports/reconciliation.ts`) resolves a staged row's portfolio THREE ways — a `kind:"portfolio"` mapping decision's `targetId` (**any** of the owner's owned portfolios, not just the batch's own target; the mapping picker offers every owned portfolio and the save action accepts any owned `targetId`), the row's own `targetPortfolioId`, or a unique portfolio NAME match — and a batch with `target_portfolio_id IS NULL` still resolves fully by name. Scoping an "existing X" comparison set to the batch's own target therefore silently misses a row that resolves elsewhere: an undetectable false negative, indistinguishable from a genuine non-match — exactly the failure mode a cap/degrade design is built to avoid, so narrowing this way just reintroduces the SAME bug class one level up. **User-wide is correct and loses no precision** whenever the check's actual matching already keys off the row's own resolved membership/portfolio-security id (`portfolio_securities.id` is unique per portfolio, and candidate resolution already filters by `candidate.portfolioId === portfolio.id`) — a portfolio-A existing fact can never match a portfolio-B row's resolved identity regardless of how wide the read is, so per-portfolio correctness comes from identity matching downstream, not from narrowing the query. Precedent for the CAP itself (not the scope): `app/historical-portfolio-value.ts`'s `MAX_X + 1` / `throw` convention — but for an ADVISORY (non-blocking) check specifically, throwing is too aggressive (it would break the whole page over one owner's large trade history for a warning that isn't even required). Instead: `LIMIT MAX + 1`, and if `rows.length > MAX`, degrade to a visible batch-level info issue (no `rowId`) stating the check wasn't run — never silently truncate the comparison set and never silently disable it either. **Before proposing ANY narrowing of a comparison set for an advisory check, trace every path that can produce the identity being compared (here, `portfolioFor`'s three branches) — not just the common-case path — or the "obvious" scoping will reintroduce exactly the false-negative failure mode the check exists to prevent.**
9. **Any `decimal()`/parsing helper called against a value loaded from the DB (as opposed to a freshly-parsed CSV/import row, which the parser already canonicalizes) needs a try/catch that fails toward "not a match" / "not applicable", not a bare throw** — a single legacy or corrupted row would otherwise 500 an entire preview page over one advisory comparison. Incoming row values, by contrast, are already guaranteed canonical by the parser upstream (`CANONICAL_DECIMAL`/`normalizeDecimalText`), so don't bother defensively guarding those — a test asserting an incoming row's malformed decimal is handled gracefully will fail for an unrelated reason (it hits the pre-existing holdings `add()`/`subtract()` arithmetic first, which is out of scope to change).
   - **CORRECTION (BUG-013):** this is true for a *malformed* value but not for a *missing* one. A `NormalizedImportRow` field added after the row schema's earliest version (e.g. `frankingPerShare`/`totalCashDecimal`/`totalFrankingDecimal`, added by IMP-006/BRK-005) deserializes as genuinely `undefined` — not `null` — on a row whose `normalized_fields_json` blob predates that field, even though the TS type declares it non-optional `string | null`. Passing `undefined` straight into a helper like `computeDividendCashTotal` (which only null-checks, `=== null`) skips the "missing" branch and falls through to `parseDecimal(undefined)`, which throws. Any NEW helper you add over an incoming row's OPTIONAL-ish/late-added fields needs its own safe wrapper (`try { real() } catch { return null/false }`) even though the field is "incoming, not DB" — the guard is about *field vintage*, not *incoming vs DB provenance*. A quick way to catch this in your own test: build the fixture by `delete`-ing the specific late-added key from a spread object rather than setting it to `null`, and assert `doesNotThrow`. Also: don't delete a BASE field (present since the schema's original version, e.g. `sharesOwned`/`costPerShare`) in the same fixture just to exercise your new guard — deleting those trips a DIFFERENT, unrelated, unguarded call site (DIV-016C's own `computeDividendCashTotal` use for `dividendReconciliationRowsAll`, which runs unconditionally for every dividend row and has no guard at all) and your test will fail for the wrong reason, at a line number that isn't yours to fix in a narrowly-scoped task.
10. **`docs/ARCHITECTURE.md`'s convention for correcting an established claim is to APPEND a bold dated note to the existing paragraph, never rewrite the original sentence** (see the BRK-005C/BRK-015 corrections already appended to the BRK-005 Idempotency paragraph) — and durable "we deliberately did NOT add a constraint" decisions (rejected alternatives) belong in the `## Decision log` section at the end of the file, dated, even when the reasoning is already spelled out in `docs/DATA_MODEL.md`.
11a. **A reconciliation advisory check must suppress itself for a row already bound for a commit-time exact-`source_reference` SKIP, or it is guaranteed noise on any re-sync of an already-fully-committed account.** (BUG-013 review round, ruling 1 — applied retroactively to BUG-011's already-shipped `TRADE_NEAR_EXISTING_ENTRY` too, which had shipped without this and would have warned on all 226 rows of a real production batch that committed 0.) The tell: an advisory check compares ECONOMIC identity (security+date+amount), but the commit-time dedupe it's warning about compares EXACT `source_reference` identity — these are different keys, and a row can satisfy the economic match while ALSO being certain to skip at commit (same content re-staged, e.g. a full re-sync). Fix: build a `${portfolioId}::import-fingerprint:${row.fingerprint}` key (this exact string — `db/repositories/import-commit.ts`'s shared `sourceReference` construction for both trade and dividend branches) and check it against a caller-supplied `existing<X>SourceReferences` set BEFORE running the advisory match; skip pushing the issue if present. Never weakens genuine cross-route detection, because a cross-route duplicate's fingerprint is a DIFFERENT format entirely (the whole reason these checks exist) and can never be in that set. When adding a NEW advisory check of this shape, ask up front "will this warn on a row the commit path was always going to skip anyway" — don't wait for a reviewer to quantify it on a fixture.
12. **A newly-WIDENED query's decimal columns are new `parseDecimal` exposure even if the underlying table's writers were always validated.** (BUG-013 review round, ruling 2.) The pre-widening query selected NO decimal columns at all — widening a query to add columns is not free even when you're reusing an existing table you didn't create; audit whether the NEW columns you're now parsing need the SAME defensive-guard treatment note 9 already established for DB-sourced values, and export the existing safe wrapper (don't reimplement it) for use at the new call site AND its test mirror.
13. **When a reviewer says "your test doesn't test what it claims," verify by running the test against the PRE-fix commit** — if it passes identically before and after, it has zero coverage of the thing it claims to guard, and the fixture (not just the assertion) is wrong. A malformed-decimal test fixture must be checked against the actual regex/validator (e.g. `domain/calculations/decimal.ts`'s `DECIMAL_PATTERN`) rather than assumed — "leading `-`" and "leading zero"/"empty string"/"trailing dot with no digits" are NOT the same failure mode, and only some of them actually throw.
14. **A source-pin regex must be anchored to its OWN query's surrounding SQL text, not just the bind array, when two queries in the same file bind identical-looking parameter arrays** (e.g. two `LIMIT ?` queries both binding `[userId, SAME_CONSTANT + 1]`) — a regex matching only the bind array passes as long as ANY occurrence in the file satisfies it, so mutating ONE query's bind (e.g. dropping `+ 1`, the exact off-by-one a cap exists to prevent) goes undetected if a sibling query's untouched occurrence still matches. Fold the full SQL text through the bind array into one regex per query.
15. **When the coordinator relays a REVIEWER's ruling verbatim, extract the exact key/predicate they specify — do not approximate.** BUG-013's ruling 1 named `source_type = 'csv_import'` with NO `status` filter as the trade dedupe's exact predicate; reproducing that exactly (rather than adding `status = 'posted'` "for safety") mattered because `import-commit.ts`'s own check has no status filter either — a REVERSED transaction's `source_reference` still counts as "will be skipped at commit," and the advisory suppression must predict that same reality, not a more conservative one.

11. **When the cap/degrade THRESHOLD logic itself needs direct unit-test coverage but lives inside a `next/headers`-blocked file** (see [[test-runner-constraints]] — `app/import-actions.ts` can never be imported by this repo's plain Node test runner because it statically imports `getAuthenticatedSqlContext`), extract JUST the pure boundary decision (e.g. `rows.length > max ? degraded : rows`) into a tiny sibling module with no such import (here, `app/import-trade-duplicate-check.ts`). Import that pure function from BOTH the real loader and any test-side query mirror (e.g. `tests/imp-004a.test.ts`'s `pagePreview`) so the cap logic is genuinely shared/tested, not re-implemented twice with room to drift. Pin the loader's WIRING to that function (that it's actually called, with the right args) via a `readFile` + `assert.match` source-text test, exactly `tests/imp-003b.test.ts`'s established pattern — never claim the source-match alone is a behavioral test of the boundary; the pure function needs its own real unit tests (at, one-over, and generously-under the cap) too.
