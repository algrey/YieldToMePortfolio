description: import_rows.commit_transaction_id is a polymorphic FK-less column (transactions.id OR dividend_manual_records.id) — any query joining on it for ONE table silently drops the other kind's committed rows.
metadata:
  type: project
---

`db/repositories/import-commit.ts`'s `import_rows.commit_transaction_id` is written by TWO different commit paths with two different target tables and no discriminator column: the ledger/trade path (`resolveInput`'s `"ledger"` kind) writes a `transactions.id`; the dividend path (`"dividend"` kind) writes a `dividend_manual_records.id`. Both set the SAME column, `commit_status = 'committed'`.

**Any code that resolves "what portfolio/date did this committed row affect" via a single `JOIN <one table> ON <table>.id = r.commit_transaction_id` silently returns zero rows for commits made entirely of the OTHER kind.** This was PRF-007 Finding A: `finalize`'s affected-portfolio query only joined `transactions`, so a dividend-only Sharesight sync commit queued no invalidation/rebuild at all. Not caught by any prior test because no test exercised a dividend-only commit's `rebuildJobIds`. NOTE (review round B3, 2026-09-01): do NOT assert this queueing gap *caused* the owner's "still had the old values" `/income` report as fact — that causal link was reviewed and found unsupported by the code (`/income` reads `dividend_manual_records` LIVE; the projection pipeline never consumes that table). The gap is real and worth fixing regardless; the symptom's true cause is a separate, still-open question (TASKS.md Findings B/C).

**Fix pattern**: resolve via a `UNION ALL` of two branches (one JOIN per table, each still scoped by `r.user_id = ?` and the target table's own `user_id` column) rather than widening one JOIN or adding a discriminator column — matches [[d1-query-planning]]'s "narrowest correct query" bias and avoids a schema change for a read-side query. See the `finalize()` affected-portfolio query for the exact shape (correlated subqueries referencing the outer `GROUP BY` column still work the same way against a `UNION ALL` subquery source).

**Two subtler correctness traps found only on review (both required a second correction commit, `77b8d40`), worth checking proactively next time a UNION-across-kinds fix like this is written:**
1. **A correlated subquery that was previously guaranteed non-NULL (because only one row-kind ever reached it) can become genuinely NULL once a second kind is unioned in.** Here, `ledger_high_water`'s `SELECT ... FROM transactions ... LIMIT 1` was safe pre-fix (every `affected` row came from a just-committed transaction, so a matching transaction always existed); once dividend-only rows entered `affected`, a portfolio with zero transactions makes it NULL. `String(possiblyNullValue)` silently produces the LITERAL STRING `"null"` — truthy, and fails a downstream `if (!x)` self-heal check wide open. Wrap any such subquery in `COALESCE(..., '')` (or the domain's established falsy sentinel) BEFORE it can reach a `String()` cast, not after.
2. **A combined range aggregated across two kinds (`MIN`/`MAX` over a `UNION ALL`) is not automatically the right range for every downstream consumer of that aggregate.** `range_from`/`range_to` feeding the queued `calculation_runs` row is fine combined (the pipeline rebuilds unconditionally regardless of range). But `portfolio_value_history` invalidation from that SAME combined `range_from` is WRONG when one kind (dividends) cannot affect that derived table at all — it would delete/force-rederive valid cache rows outside the actually-affected date span. Tag each UNION branch with a kind-specific nullable column (e.g. `trade_effective_date`, NULL on the dividend branch) so a kind-specific consumer can `MIN()`/filter on just its own subset, independent of the combined aggregate other consumers use.

**How to apply**: before writing or reviewing ANY query that joins on `import_rows.commit_transaction_id`, grep both write sites (`db/repositories/import-commit.ts`'s dividend and ledger branches) to confirm which table(s) it can point at, and check whether the query needs to cover both. If a THIRD commit kind is ever added to this codebase, every such query needs a third UNION branch — and re-check both traps above for it.

**Test-fixture gotcha reused across `tests/imp-006.test.ts`, `tests/brk-005.test.ts`, `tests/prf-007.test.ts`**: `stageRow`/`buyRow`/`dividendRow` helper triples for staging import rows directly (bypassing CSV parsing) are duplicated per test file, not shared. `import_rows.id` is a GLOBAL primary key (not scoped per batch/user) — reusing a literal like `"row-1"` across two batches or two users in the same in-memory DB throws a UNIQUE constraint error; give every staged row a batch/user-unique id.
